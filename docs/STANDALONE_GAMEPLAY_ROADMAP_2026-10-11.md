# HeroList — лучшие автономные игровые системы конкурентов и план их внедрения

**Дата исследования:** 11 октября 2026 г.  
**Проект:** HeroList / «Лист Героя 5e»  
**Целевой раздел:** `/adventure/` → игровая копия персонажа  
**Базовая точка сравнения:** исходники `main`, документация `docs/GAME_MODE_1_6.md` (1.6.1)  
**Статус:** исследование + продуктовая спецификация; **не список уже внедрённых изменений**.

> **Граница задачи.** Только личный игровой помощник для **одного** персонажа, которым пользуется один человек на одном устройстве. **Не реализовывать сейчас**: онлайн-комнаты, совместную игру, чат, карты, токены, виртуальный стол, управление монстрами, интерфейс мастера, групповую инициативу, синхронизацию с другими персонажами. Даже если функция конкурента работает в VTT, здесь рассматривается только её **автономная часть**, применимая в листе героя.

---

## 0. Короткий вывод

**Конкурентоспособный автономный игровой режим — не ещё один лист с большими кнопками.** Он отвечает за текущее состояние героя и безошибочно проводит цепочку «выбрать действие → увидеть стоимость и модификаторы → бросить кости → применить результат к СВОЕМУ листу → сохранить историю».

Наиболее ценные референсы:

1. **Long Story Short:** «заряженная дайсница» с разбором каждого слагаемого броска; слои включаемых/отключаемых бонусов.
2. **Roll20 5e:** единая боевая панель, куда попадают действия из оружия, заклинаний и особенностей, вместо необходимости искать их в отдельных справочниках.
3. **D&D Beyond:** общая секция ограниченных использований, короткий/долгий отдых, экипировка и настройка предметов, простой доступ к рабочим действиям.
4. **Fight Club 5th Edition:** единая связь экипировки с вычисляемыми показателями и быстрый доступ к заклинаниям, предметам и пользовательским броскам.
5. **HexSheet:** заявленные быстрые боевые действия, постоянный учёт концентрации/состояний, автоматические бонусы предметов, формы и спутники; **ориентир концепции, заявления поставщика, а не независимый тест каждой функции**.
6. **PrismScroll:** удобство мобильного листа при управлении одной рукой, локальность персонажей и самостоятельный экспорт.
7. **Foundry D&D 5e:** модель структурированных действий, требований, ресурсов и активных эффектов (берём принципы из движка листа, не VTT).

**Главные цели реализации:**

- Расширить уже созданный игровой режим, **не создавать второй**.
- Связать броски, характеристики, способности, предметы, заклинания и эффекты одним вычислительным слоем.
- Убрать повторное ручное введение одних и тех же бонусов.
- Максимум автоматизации там, где данные достоверны, и **честный ручной режим** там, где контекст знает только мастер.
- Сделать основные действия достижимыми за **1–2 нажатия**, но не запускать необратимые траты ресурсов от случайного касания.

## 1. Что проверено и как читать сравнение

Источники — публичная официальная документация/страницы продуктов; локальная реализация — `main` в репозитории HeroList. Указание возможности у конкурента означает, что она **описана поставщиком**, а не обязательно проверена в авторизованном пользовательском сеансе. Особенно осторожно интерпретировать маркетинговые страницы.

| Конкурент | Подтверждённая автономная функция | Конкретная идея для HeroList | Ограничение сравнения |
|---|---|---|---|
| **Long Story Short (LSS)** | Слои бонусов: база/модификатор/перезапись; деактивация бонусов; разложение броска и ручной доброс; преимущество/помеха | `ModifierEngine` + подробный `RollComposer` | Не копировать UI, символы или алгоритмы бездумно; реализовать собственную механику |

## 4. ST-01 — единый движок бонусов и вычисляемых показателей (P0)

### Что взять у конкурентов

LSS поддерживает слои **базовое значение → модификаторы → принудительная замена**, и каждый бонус можно отключить. Roll20 стремится автоматически рассчитывать значения из листа и поддерживает настраиваемые модификаторы. Лучшее решение для HeroList — вынести вычисления из JSX и локальных спецслучаев в **единый `resolveStat` / `resolveRoll`**.

### Требования

1. Каждый бонус имеет **источник**: класс, черта, раса, предмет, активный эффект, состояние, ручная поправка, Homebrew.
2. Каждый бонус знает **область**: КД, инициатива, скорость, конкретный тип атаки, проверка навыка, спасбросок, урон, атака заклинанием, Сл заклинания, максимальные HP и т. п.
3. Разделить модификаторы по поведению: `add`, `setBase`, `setMinimum`, `replace`, `advantage`, `disadvantage`, `diceBonus`, `multiply` **только когда правило допускает**.
4. **Нельзя просто суммировать всё.** Бонус конкретного магического меча привязан к его атакам. Бонус отдельного фокуса действует на магию соответствующего источника. Одинаковые эффекты/условия должны разрешаться по правилам 2014/2024.
5. Проверять требования: предмет экипирован; для настройки она действительно завершена; нужный класс; эффект активен; используется правильный вид оружия; сохранён запас ресурса.
6. Выдавать не только число, но и **объяснение**: `КД 17 = кольчуга 16 + Защитный стиль 1`, откуда взята каждая часть, какие кандидаты исключены и почему.
7. Разделить **постоянные, включаемые и одноразовые** эффекты. Одноразовый бонус в броске не становится постоянным бонусом персонажа.
8. Изменение условий автоматически пересчитывает результат, не переписывая базовые значения героя.
9. Не допускать двойного применения бонусов между `characterRules`, `playDerived`, `itemBonus`, `weaponItemBonus`, `spellItemBonus`, `hbEffects`.

### Предлагаемый контракт (псевдо-TypeScript)

```ts
type Modifier = {
  id: string;
  source: { kind: 'class'|'race'|'feat'|'item'|'effect'|'condition'|'homebrew'|'manual'; id: string; label: string };
  target: string;                         // 'ac', 'attack:rapier', 'spell:dc:wizard', ...
  operation: 'add'|'setBase'|'setMinimum'|'replace'|'advantage'|'disadvantage'|'diceBonus';
  value: number | SafeDiceAST;
  enabled: boolean;
  predicate?: RulePredicate;               // декларативные условия, без eval
  stackingGroup?: string;                 // для явно регламентированного сложения
  durationEffectId?: string;
};

type ResolvedValue = {
  total: number;
  included: { modifierId: string; value: number; explanation: string }[];
  excluded: { modifierId: string; reason: string }[];
  warnings: string[];
};
```

**UI:** рядом с любым числом — маленькая кнопка «i» / «Откуда значение?». В открывшемся окне — активные составляющие и приглушённые неприменимые. Для ручных модификаторов предусмотрен переключатель.

**Критерии приёмки:** +1 фокус меняет только разрешённую магическую атаку/Сл; +1 рапира меняет только атаку и урон рапиры; снятие предмета убирает бонус; эффект истекает — значения пересчитываются; два разных источника не удваивают один и тот же эффект из-за повторного прохода логики.

## 5. ST-02 и ST-12 — лучшая система бросков (P0/P1)

### Референс: LSS «заряженная дайсница»

Обычный клик запускает бросок; Shift-клик на ПК или удержание на телефоне открывает редактор броска. В нём можно выбрать преимущество/помеху, выключить отдельные бонусы, добавить формулу и сделать критический урон, когда он законен.

### Как улучшить в HeroList

**Два режима взаимодействия:**

- **Мгновенный бросок** — уже существует. Одно нажатие, актуальные бонусы, сразу результат.
- **Подготовить бросок** — вторичная кнопка или ПК `Shift+click` / мобильное отдельное меню (`long press` как альтернативный, **не единственный** способ). Показать составляющие, настройки и предварительный итог формулы.

Пример:

```text
АТАКА — Рапира +1                        [Подготовить]
1d20 + 7
  [✓] Ловкость                       +4
  [✓] Бонус мастерства               +2
  [✓] Рапира +1                      +1
  [ ] Благословение                  +1d4
  [ ] Ситуационный бонус            +2
  Режим: (● Обычный) (○ Преим.) (○ Помеха)
  [БРОСИТЬ]   [Сохранить как пресет]
```

**После броска** показывать `итог / натуральная кость / каждое слагаемое / источник`. Для преимущества/помехи — обе d20 и выделение выбранной. Результат должен быть восстановим в журнале.

**Поддерживаемые пресеты:** `1d20`, `2d6`, `1d100`, `4d6kh3` (только после расширения парсера), «Скрытность», «Инициатива с ручным бонусом», «Урон основного оружия». Пользователь может закрепить 3–8 пресетов.

**Урон и крит:** умножать **кости**, которые подлежат криту, не постоянный числовой бонус; тип урона и дополнительные условные кости хранить отдельно. Спасбросковые заклинания **никогда не получают крит от результата спасброска**. Нельзя автоматически включать крит для эффектов без атаки.

**Кубики справа** на ПК и в доступном мобильном окне сохранить. Показывать каждое выпавшее значение, сумму и хотя бы 3 недавних броска — это уже есть; развить выбор цвета лишь как декоративную настройку, не как отдельную механику.

**Сохранение серии бросков**: серия `Атака → Урон` должна сохраняться как одно логическое событие с дочерними бросками, не стирая факт отдельных результатов.

## 6. ST-03 и ST-07 — единый каталог и быстрые действия (P0/P1)

### Референс: Roll20 Combat Tab + HexSheet Quick Actions

Сегодня навыки находятся в «Герое», атаки в «Действиях», заклинания в «Магии», расходники в «Рюкзаке», способности — в разных разделах. Это нормально для справочника, но во время боя требует лишних переходов.

### Целевая схема

**Любое применимое умение — единый `PlayAction`:** атака оружием, заговор, заклинание, действие предмета, действие класса, бонусное действие, реакция, пользовательская способность, стандартное действие. Источник остаётся там, где он есть; единая панель лишь **собирает доступные операции**.

```ts
type PlayAction = {
  id: string;                       // стабильный id сущности + варианта
  source: { kind: 'weapon'|'spell'|'feature'|'item'|'custom'|'standard'; id: string };
  name: string;
  economy: 'action'|'bonus'|'reaction'|'free'|'special'|'timed';
  availability: RulePredicate[];
  costs: ResourceCost[];
  steps: ActionStep[];               // атака, спасбросок, урон, лечение, эффект, трата
  tags: string[];
  favorite?: boolean;
  manualFallback?: string;
};
```

**Боевой HUD** (`Действия`):

```text
ГЕРОЙ   HP 27/32   Врем. 5   КД 17   Концентр.: Благословение
[Основное оружие] [Избранные] [Атаки] [Магия] [Способности] [Предметы]

★ Рапира +1        Действие         [Атака +7] [Урон 1d8+5]
★ Лечащее слово    Бонусное         [Сотворить…]  2/3 ячеек
★ Второе дыхание   Бонусное         [Использовать]  1/1
★ Зелье лечения    Действие         [Выпить]  ×2

Действие: свободно · Бонусное: потрачено · Реакция: свободна
```

**Функции:** избранное (в том числе пользовательское), группировка по типу действия и доступности, поиск, фильтр «Можно сейчас», метки «нет слотов»/«нет патронов», подробности без ухода на другую вкладку.

**Не делать скрытую автоматику:** сам бросок атаки не равен расходу действия. В карточке `Использовать` можно предложить отметить действие и списать ресурс **одним подтверждённым переходом**; игрок вправе отключить автоматическое ведение экономики действий. Реакция вне собственного хода должна корректно помечаться потраченной до восстановления по правилам.

**Критерий:** обычное оружие, фокус, классовая способность и пользовательский эффект действуют через одну архитектуру, а не через 4 разных `onClick` с независимым подсчётом.

## 7. ST-04 — полноценная магия без «угадывания по описанию» (P0)

### Что сохранить

У HeroList уже есть `spellPlayProfile`, источники мультикласса, Pact Magic, расовые использования, масштабирование части заговоров и заклинаний, правильное отличие атаки от спасброска. Всё это **расширять**, не заменять другим каталогом.

### Главная проблема

Часть механик сейчас извлекается регулярными выражениями из `description`. Это допустимый **резервный режим**, но не основание для уверенной автоматизации. Одно заклинание может делать несколько независимых атак, несколько типов урона, выбирать способности по ситуации, требовать повторных спасбросков или содержать эффект с иным моментом срабатывания.

### Ввести машиночитаемую механику

```ts
type SpellMechanics = {
  delivery: 'spellAttack'|'weaponAttack'|'savingThrow'|'autoHit'|'healing'|'utility'|'mixed';
  save?: { ability: AbilityKey; effect: 'none'|'half'|'full'|'special' };
  attackCount?: FormulaAST;              // лучи/попадания рассчитываются отдельно
  steps: Array<
    | { kind: 'attack'; attackKind: 'meleeSpell'|'rangedSpell'|'weapon' }
    | { kind: 'damage'; formula: SafeDiceAST; damageType: string; critEligible: boolean; target: 'self'|'other' }
    | { kind: 'heal'; formula: SafeDiceAST }
    | { kind: 'save'; ability: AbilityKey; onSuccess: string; onFailure: string }
    | { kind: 'effect'; effectId: string; application: 'self'|'manual' }
  >;
  upcast?: StructuredScaling;
  casterSourcePolicy?: string;
  support: 'verified'|'partial'|'manual';
};
```

### Окно «Сотворить» должно показывать

1. **Источник магии:** класс (особенно при мультиклассе), раса, черта, предмет или Homebrew.
2. **Способ оплаты:** ячейка выбранного круга, договорная ячейка, расовый/классовый ресурс, предметный заряд, бесплатное использование, ритуал или отдельное разрешённое правило.
3. **Параметры:** компонентность, время наложения, концентрация, дистанция, длительность, Сл, бонус попадания.
4. **Что произойдёт после подтверждения:** ресурс −1, начнётся/заменится концентрация, появятся конкретные броски/эффекты.
5. **Поддержка механики:** `Автоматически` / `Частично` / `Только описание и ручной бросок`.

**Примеры:**

- **Огненный снаряд (Fire Bolt):** атака заклинанием, масштабирование по общему уровню персонажа; крит лишь по атаке.
- **Огненный шар (Fireball):** Сл Ловкости, подходящие кости урона, настройка «при успешном спасброске половина» в подсказке; **никакого крита**.
- **Волшебная стрела (Magic Missile):** автоматическое попадание, отдельные дротики/распределение целей вручную; **никакого броска атаки и крита**.
- **Палящий луч (Scorching Ray):** отдельная атака каждого луча, допускается отдельный крит каждого луча; удобно делать серию без повторного расхода ячейки.
- **Метка охотника / Проклятие:** привязка бонусных костей к подходящим будущим атакам и к действующей концентрации — **после** реализации общего эффекта.
- **Лечащее слово:** правильный модификатор того класса, которым сотворено заклинание; шкала повышения круга выбирается до расхода.
- **Ритуал:** только при наличии соответствующего права, без ячейки, с корректным временем; ритуальный признак в каталоге сам по себе не разрешает ритуальное сотворение всем классам.
- **Заклинание от предмета:** использовать формулу/Сл/заряды и характеристику, предписанные *конкретным предметом*, а не слепо подставлять основной класс.

### Правила безопасности транзакции

- **На `Отмена` до подтверждения** ячейка и заряды не тратятся.
- После подтверждения стоимость расходуется **ровно один раз**; следующие лучи/длительные эффекты не списывают повторно.
- Проверять допустимость нескольких заклинаний за ход по **выбранной редакции** (2014 и 2024 различаются); если не удаётся доказать запрет, показывать мягкое предупреждение, а не блокировать без права отмены.
- Если данные неполны, **никогда не выдумывать бросок атаки, автоматический крит, Сл, лечение или расход**.
- Некорректный профиль Homebrew должен открываться в ручном режиме с объяснением, а не ломать карточку.

## 8. ST-05 — концентрация и жизненный цикл эффектов (P0)

### Предлагаемая модель

Вместо текущей упрощённой записи `{name, remaining}` создать `ActiveEffect` с `sourceId`, временными правилами и конкретными модификаторами:

```ts
type ActiveEffect = {
  id: string;
  source: { kind: 'spell'|'feature'|'item'|'condition'|'manual'; id: string };
  name: string;
  startedAtGameTime?: number;
  duration: { kind: 'rounds'|'minutes'|'hours'|'untilRest'|'untilDismissed'|'unknown'; value?: number };
  expiry: 'startOfOwnTurn'|'endOfOwnTurn'|'elapsedTime'|'shortRest'|'longRest'|'manual';
  concentrationOwner?: 'self';
  modifiers: Modifier[];
  remaining?: number;
  notes?: string;
};
```

**Концентрация:** только одна концентрация героя. Новый концентрационный эффект прекращает старый в точке, которую предписывают правила соответствующей редакции; все бонусы предыдущего эффекта удаляются. Получение разных источников урона → отдельные проверки. Урон, поглощённый временными HP, тоже требует правильной проверки согласно правилам. При потере дееспособности концентрация прекращается. Для **2024** у Сл проверки концентрации есть верхняя граница **30**; не переносить её без проверки в механику 2014.

**Таймер:** собственный ход не является универсальным мировым часом. Поэтому:

- разрешить пользователю `Следующий собственный ход`, `+1 раунд` и `Прошло 1/10/60 минут`;
- эффекты с длительностью в раундах явно предупреждают: «отсчёт по собственным ходам приблизителен»;
- не удалять эффект автоматически по неизвестной длительности;
- длительные эффекты без концентрации могут продолжаться во время отдыха, если конкретное правило это допускает;
- завершение концентрации не должно удалять независимые от неё состояния.

**UX:** на HUD мини-чипы активных эффектов (название, осталось времени, значок концентрации, снять) и значок «Есть непройденная проверка концентрации». Под каждым бонусом доступно «Эффект: источник».

## 9. ST-08 — состояния, сопротивления и истощение (P1)

Сейчас список состояний существует, но механические последствия в значительной степени остаются на игроке. Ввести **правила только для заведомо известных контекстов**, сохранив переключатель «решение мастера / вручную».

| Состояние / эффект | Что автоматизировать | Что НЕ решать без контекста |
|---|---|---|
| Отравлен | Помехи релевантным атакам и проверкам характеристики по редакции | Источник отравления и длительность без данных |
| Сбит с ног | Собственные атаки/перемещение — явные подсказки; в зависимости от контекста преимущества других | Дистанцию внешнего атакующего |
| Ослеплён | Пометка невозможности видеть и типичных последствий для своих атак | Видит ли герой конкретную цель и через какой сенсор |
| Схвачен / опутан | Скорость, релевантные ограничения | Автоматически решать освобождение без Сл |
| Недееспособен / парализован / бессознателен | Запрет явно несовместимых собственных действий, концентрацию | Делать броски/изменять чужих существ |
| Истощение | **Раздельные правила 2014 и 2024**: 2024 — штраф к D20 tests и скорости, 2014 — ступенчатые эффекты | Смешивать редакции |
| Сопротивления/уязвимости | Вывод защит героя и расчёт входящего урона **по типу** | Угадать тип урона, если он не введён |

**Входящий урон:** поле `тип урона`, перечень действующих защит, итог после сопротивлений и уязвимостей, затем временные HP → обычные HP → концентрация и спасброски смерти. В 2014/2024 необходимо правильно учитывать **порядок и округления**, а также отдельные типы в одном событии.

**Правила 2024:** истощение уменьшает результат D20 Test на `2 × уровень истощения`, скорость — на `5 футов × уровень`, смерть при уровне 6. В 2014 — **другие эффекты**; требуется отдельная таблица. Допускается «только предупредить» для ситуаций с дистанцией, освещением и третьими лицами.

## 10. ST-09 и ST-11 — инвентарь как настоящая игровая система (P1)

### Что взять у Fight Club и D&D Beyond

Экипировка должна непосредственно влиять на показатели, а список вещей — служить для действий: надеть, выпить, использовать, перезарядить, разделить стопку. Эти возможности **частично уже присутствуют** в `PlayInventory.tsx` и `adventure.ts`. Новая задача — сделать модель предмета точнее и убрать ручные операции там, где правило известно.

### 10.1 Каталог и категории

Разделить **определение предмета** и **конкретный экземпляр у героя**:

```ts
type ItemDefinition = {
  id: string;
  name: string;
  category: 'weapon'|'armor'|'shield'|'focus'|'consumable'|'ammunition'|'gear'|'container'|'wondrous';
  source?: { book: string; edition: '2014'|'2024'|'both' };
  weight?: number;
  price?: CurrencyValue;
  equipmentRules?: EquipmentRules;
  actions?: PlayActionDefinition[];
  effects?: ModifierDefinition[];
};

type ItemInstance = {
  id: string;
  definitionId?: string;
  customName?: string;
  quantity: number;
  containerId?: string;
  equippedSlot?: string;
  attuned: boolean;
  chargesSpent?: number;
  customOverrides?: Partial<ItemDefinition>;
};
```

**Плюс по отношению к конкурентам:** несколько экземпляров одного оружия (обычная рапира, рапира +1) должны отличаться `instanceId`; атака и бонус привязываются к **конкретному экземпляру**, а не к сравнению русских названий регулярным выражением. Так исключается ошибка «бонус одного из двух одинаковых мечей применяется к не тому».

### 10.2 Экипировка

- Слоты экипировки: основная рука, другая рука, броня, щит, фокус, аксессуары (без искусственного запрета всех исключительных комбинаций).
- КД с расчётом по доспехам, особенностям классов и активным эффектам; отдельно показать причины выбора формулы.
- Вкладка предмета: надеть/снять, использовать, количество, настройка, заряды, источник действия, заметка.
- Магические бонусы `+1/+2/+3` как **политика соответствующего предмета**: оружие (атака и урон), фокус (атака заклинанием и/или Сл — **только если конкретный предмет даёт эти бонусы**), броня/щит (КД), другие свойства.
- Проверки настройки: максимум (по умолчанию 3), исключения от особенностей класса, завершение нужного отдыха, ограничения самого предмета, запрет двух настроек одного конкретного предмета.
- Проклятия не снимаются обычным «отменить настройку», если это противоречит правилу предмета; сохраняется возможность ручного решения мастера.
- Не суммировать автоматически бонусы по всем одновременно надетым магическим фокусам. Используемый фокус/правило конкретного заклинания должны быть определимы.

### 10.3 Контейнеры и вес

- Строковые «места хранения» мигрировать постепенно в необязательный `containerId`.
- Масса: `quantity × weight`, иерархия вложений без циклов; доспех **по-прежнему несёт вес**, если правила/предмет не оговаривают другое.
- Отдельно: «при себе», «в рюкзаке», «оставлено в лагере», «на хранении»; **место хранения влияет на доступность действия**, а не удаляет предмет.
- Превышение нагрузки — подсказка/режим по выбранной редакции и настройке группы; не навязывать опциональную механику всем.
- Расходники: быстрое «использовать один», «выпить с броском лечения», автоматическое уменьшение количества **по подтверждённому действию**.
- Боеприпасы: предложить вычесть при дальнобойной атаке, но предоставить переключатель для бесконечных/неучитываемых боеприпасов и возврата.
- Разделение стопок, перенос между своими контейнерами, пометка «передано/оставлено» без изменения чужих листов.

### 10.4 Деньги

- Монеты разных номиналов, получение/трата в журнале, конвертация номиналов **только как отдельное действие** (сумма не должна незаметно изменять состав монет).
- Быстрый расход с подтверждением: цена покупки и видимые остатки.
- Не вводить рынок, магазин мастера, цены кампании или удалённую передачу валюты.

**Критерии приёмки:** два экземпляра одного оружия дают разные атаки; снятый/не настроенный предмет не даёт бонуса; зелье лечит и списывается единым событием; отрицательное количество и циклические контейнеры невозможны; перенос в лагерь не превращает предмет в «потерянный».

## 11. ST-10 — один центр ресурсов и корректный отдых (P1)

### Референс: D&D Beyond Limited Use

Характерная сильная идея — в одном месте показывать **все способности с ограниченными использованиями**, вне зависимости от происхождения. У HeroList отдельные классные ресурсы уже есть в `characterResources.ts`, но в игровом интерфейсе ресурсы, слоты, заряд предмета и ограниченные расовые умения всё ещё живут в разных местах.

### Привести к `ResourcePool`

```ts
type ResourcePool = {
  id: string;
  label: string;
  sourceId: string;
  maximum: number | FormulaAST;
  spent: number;
  recharge: Array<'shortRest'|'longRest'|'dawn'|'levelUp'|'manual'|'custom'>;
  rechargeAmount?: number | FormulaAST;      // не всегда «до максимума»
  relation?: { poolId: string; conversionRule: string };
};
```

**В одном списке:** ярость, второе дыхание, Ки/очки дисциплины, очки чародейства, вдохновения, классовые кости, расовые применения, ячейки, Pact Magic, способности черт, заряды предметов, структурированные Homebrew-ресурсы. При этом **ячеечная система сохраняет отдельный удобный интерфейс магии**; объединяется механизм, не обязательно визуальная вкладка.

### Отдых как предварительный просмотр

```text
КОРОТКИЙ ОТДЫХ
Кости хитов: Воин d10 — 2, Колдун d8 — 0
Восстановятся: Договорные ячейки 2/2; Второе дыхание 1/1
Не изменятся: обычные ячейки волшебника
Настройка: завершить «Кольцо защиты» [✓] (если допустимо)
[Провести отдых]     [Отмена]
```

- Учитывать мультикласс, конкретные правила классов, особенности, меняющие восстановление, и 2014/2024.
- Восстановление **на рассвете** не равно продолжительному отдыху: кнопка `Наступил рассвет` уже есть, её сохранить, включить только соответствующие предметы/особенности.
- Если есть выбор потратить кости хитов, показать броски и суммарное лечение до фиксации состояния.
- Умения вида «раз в день», «раз за отдых», «получает N зарядов, а не все», требуют отдельных правил восстановления.
- Не делать слепой reset всех ресурсов из Homebrew; если `recharge` неизвестен — ручной режим с пояснением.
- После отдыха — одно событие журнала с подробностями; доступно восстановление предыдущего состояния через отмену.

**Особая осторожность:** предметные заряды, восстановление ячеек волшебником, отдельные возможности паладина, монаха, друида и чародея отличаются по правилам. Ресурсный реестр — инфраструктура, но **не замена правил класса**.

## 12. ST-13 — сменные формы, компаньоны и управляемые существа БЕЗ VTT (P2)

Эта система полезна одному игроку, хотя монстры, карта и партия не входят в текущий релиз.

### Референс: HexSheet (заявленные companions/summons)

**Не путать** спутника героя с мастерским списком монстров. Предлагаемый `PersonalCompanion` — дополнительная локальная карточка, прикреплённая к **данному** персонажу.

### Типы

1. **Дикая форма друида:** временный профиль характеристик, КД, скорости, атак/особенностей, правило HP по редакции/подклассу; явные изменения при входе и выходе.
2. **Призванное существо:** своя локальная карточка HP, действия, время действия, необходимые команды/условия, ссылка на активное заклинание; завершение при истечении или потере концентрации, если это прямо следует из источника.
3. **Фамильяр/классовый спутник:** компактная карточка, короткие заметки, запас здоровья, особые действия.
4. **Временная трансформация персонажа:** другой набор статов/атак, но базовый герой не переписывается навсегда.

### Важная архитектура

```ts
type PersonalForm = {
  id: string;
  label: string;
  sourceId: string;
  rulesEdition: '2014'|'2024';
  statOverrides: Modifier[];
  hitPointModel: 'separatePool'|'temporaryHp'|'sharedPool'|'manual';
  actions: PlayActionDefinition[];
  restrictions: RulePredicate[];
  linkedEffectId?: string;
};
```

**Внимание:** 2014 и 2024 «Дикая форма» имеют существенные различия, прежде всего в вопросах здоровья/временных HP. **Нельзя сделать один универсальный алгоритм**, который молча применяется к обоим. Первым сделать ручную форму с корректным сохранением оригинального листа, затем — полностью поддерживаемые распространённые случаи с маркировкой редакции.

**UI:** в верхнем HUD кнопка `Текущая форма: обычная / Волк / ...`. На мобильном — переключение формы отдельной доступной кнопкой. Весь лист героя остаётся восстановимым; возврат из формы не удаляет экипировку и не переопределяет перманентные способности.

## 13. ST-14 и ST-16 — интерфейс: не повторять перегруженные листы (P2)

### Принцип

**Сначала действие, потом справочник.** Full character sheet нужен, но во время сессии пользователь чаще меняет HP, тратит ресурс, атакует, кастует и смотрит активный эффект.

### Компоновка ПК

- **Постоянный HUD:** HP (вкл. временные), КД, скорость, концентрация, состояния, важные ресурсы.
- **Слева/центр:** избранные и выбранный раздел («Действия», «Магия», «Рюкзак», «Герой», «Журнал»).
- **Справа:** уже реализованная постоянно видимая панель кубиков; необязательная компактная история.
- **Сверху:** выход в Таверну, состояние сохранения, экспорт, настройки, возврат к редактору игровой копии.
- **Исключить горизонтальные скачки:** открытие деталей действия не должно перерисовывать весь HUD или смещать закреплённые кнопки.

### Компоновка телефона

- **Доступность одной рукой:** важные действия не за краем экрана, нижняя навигация уже есть.
- Длинное удержание — опциональный расширенный бросок; **всегда** должна быть и явная кнопка меню.
- При открытии окна не должна прыгать страница; можно закрыть `Esc`/системной кнопкой назад и вернуть фокус.
- Размер кнопок не менее удобного touch-target; поиск и фильтры не занимают пол-экрана.
- Не показывать сразу 40 развёрнутых карточек заклинаний: компактная строка + описание по нажатию.

### Визуальный язык HeroList

- **Наследовать обе существующие темы**, созданные настройки размеров/шрифтов/цветов и характерные рамки, шрифт, контраст. Не рисовать новый чужеродный «мобильный дашборд».
- Не добавлять полупрозрачность как дефолтный стиль; у светлой темы сплошные поверхности, выбранные состояния — усиленная рамка и насыщенный текст.
- Цвет **никогда не единственный носитель смысла**. Использовать текст, значок и подпись.
- SVG line-art для действий/категорий, совместимый с перекраской CSS-маской; не вставлять растровые декоративные кнопки, которые противоречат общему дизайну.
- Персональные пресеты HUD: «Компактный», «Подробный», «Маг», «Воин», «Мобильный» — как необязательное развитие.

### Встроенные подсказки

По умолчанию **не** загромождать интерфейс обучением. При нажатии `?` — «Почему именно +7?», «Почему нельзя применить заклинание?», «Что восстанавливается после отдыха?», «Почему предмет не даёт бонус?». Новичку — чуть больше явных подсказок; опытному — компактнее.

## 14. ST-06 и ST-15 — журнал, атомарные изменения и сохранение (P0/P2)

### Что плохо в простом `onChange`

Сейчас лог хранит последние 150 записей, а стек отмены находится в состоянии компонента. Это делает сложные последовательности (заклинание: списать ячейку, начать концентрацию, бросить лучи; зелье: списать предмет, исцелить) рискованными при перезагрузке и отмене.

### Предлагаемый метод: транзакции

```ts
type PlayTransaction = {
  id: string;
  createdAt: string;
  actorCharacterId: string;
  kind: 'attack'|'cast'|'useItem'|'rest'|'applyDamage'|'heal'|'changeEquipment'|'manual';
  summary: string;
  operations: PlayOperation[];
  dice?: DiceResult[];
  ruleEdition: '2014'|'2024';
  undo?: PlayOperation[];         // обратные операции либо ограниченный снимок изменённых полей
  correlationId?: string;        // дочерние атаки одного заклинания
};
```

**Требования:**

1. Одна подтверждённая операция — одно атомарное изменение игрового состояния и одна запись журнала.
2. `Undo` после обновления страницы по **сохранённой** истории: либо persist последних обратимых событий, либо persist ограниченных снимков. Текущий журнал текстовых сообщений этого не обеспечивает.
3. **Не перекидывать уже выпавшие кости** после восстановления, перепросмотра или отмены. Результат — неизменяемое событие; откатываются только последствия.
4. Отображать отметку «отменено», не удалять исторический факт броска без следа. В интерфейсе по умолчанию можно скрывать отменённые события.
5. Ограничить глубину (`например 20–50`) и размер хранения; долговременный журнал не обязан быть бесконечным.
6. Редактирование заметок допускает более простой debounce, но не должно уничтожать последний подтверждённый бросок.
7. Автоматическое сохранение **уже существует**, его не заменять новой серверной инфраструктурой: расширить локальный JSON и обрабатывать неудачное сохранение.
8. Резервный JSON — всегда доступен пользователю. Не называть облачную синхронизацию обязательным offline-режимом.

### Offline

Проверить фактический режим работы при отсутствии сети. Если браузер не имеет закешированного приложения, работа полностью офлайн **не гарантирована**. Дополнительная фаза: PWA/service-worker с версионированием статических ресурсов, безопасной стратегией для обновлений и отчётливым индикатором `Локально сохранено / Не синхронизировано / Ошибка сохранения`. Не кешировать токены авторизации и приватные API-ответы по умолчанию.

### Защита данных

- **Никогда не перезаписывать** `.env`, SQLite, `uploads`, пользовательские аккаунты или существующие приключения при выпуске frontend-обновления.
- Сохранять обязательный Telegram auth, механизм legacy-восстановления и существующий поток `/api/vault`.
- Не использовать `eval`/`Function` для кубиков, формул и Homebrew; парсер должен быть ограниченным и безопасным.
- При повреждённом или неизвестном поле игры загрузка персонажа не должна приводить к пустому листу: валидатор, fallback, экспорт исходного JSON.

## 15. Правила D&D 2014 и 2024: отдельные политики, а не смесь

**Ключевое требование:** механическая редакция правил — **самостоятельное поле персонажа**; внешний дизайн экспортируемого листа 2014/2024 на неё не влияет. Персонаж 2014, открытый в красивом листе 2024, не меняет правила отдыха и заклинаний.

| Область | Различие / осторожность |
|---|---|
| Истощение | 2014 — ступенчатая таблица; 2024 — штраф `−2 × уровень` к D20 tests и снижение скорости `−5 ft × уровень` |
| Кости хитов после длинного отдыха | Использовать политику выбранной редакции; 2014 — обычно восстановление до половины общих костей, минимум одну; 2024 — отдельная политика полного восстановления |
| Концентрация | Основные принципы общие, но для 2024 Сл при уроне ограничена сверху 30; корректно учитывать момент прекращения от новой концентрации |
| Несколько заклинаний в один ход | В 2014 особые ограничения для bonus-action spell; в 2024 — правило использования ячеек в пределах хода и возможные исключения; не сводить к «только одно заклинание» |
| Действия и экономика | Различия в терминологии и применении отдельных способностей; не принуждать игрока к несуществующему действию |
| Владение оружием / Weapon Mastery | Это часть правил 2024, не должна автоматически появляться у героя 2014 |
| Дикая форма | Различается модель выживаемости и взаимодействия с HP; обязательно отдельные профили |
| Лечение / заклинания | Отдельные варианты заклинаний в каталогах 2014/2024; не подменять старое описание новым |
| Особенности классов | Отдельные уровни получения и ресурсы; нельзя обновить только отображение, оставив расчёт другого года |

**Практическая схема:** `RulesetPolicy` (`2014` / `2024`) содержит функции/таблицы для наиболее чувствительных подсистем. У каждой способности и заклинания — `rulesEdition` или совместимая версия. При отсутствии нужного варианта показывать явно `Правило не автоматизировано; используйте ручной расчёт`, а не подсовывать механику другой редакции.

**Источник правил:** официальные [Basic Rules 2014](https://www.dndbeyond.com/sources/dnd/basic-rules-2014) и [Free Rules 2024](https://www.dndbeyond.com/sources/dnd/br-2024). Не копировать защищённые тексты чужих книг из коммерческих сервисов: использовать только контент с надлежащими правами/лицензиями и собственную структуру данных.

## 16. Homebrew: механики из редактора должны работать в игре

Перенос HB из редактора в Adventure — одно из самых перспективных отличий HeroList. **Но** домашняя способность, указанная только текстом, не становится автоматически исполняемым правилом.

### Ввести 3 уровня поддержки

| Уровень | Данные | Игровой результат |
|---|---|---|
| **1 — Полная механика** | Тип действия, источник, стоимость, формула, проверка, урон/лечение, длительность, восстановление, условие | Кнопка `Использовать`, автоматическая законная часть и журнал |
| **2 — Частичная механика** | Есть формула и ресурс, но сложные условия/цели | Бросок + расход по подтверждению + явное предупреждение о ручном разрешении |
| **3 — Справочное действие** | Только описание | Карточка/заметка и произвольный кубик; **без выдуманных эффектов** |

### Поддержать в Homebrew Editor

- Тип действия (`action`, `bonus`, `reaction`, особое).
- Цена (`resourceId`, количество, ячейка, заряды предмета, расходник).
- Бросок атаки/спасбросок и характеристика.
- Составные формулы урона с типом, критом, масштабированием по уровню персонажа/класса/слота.
- Условия применения и состояния «активен/неактивен».
- Длительность и восстановление; связь с концентрацией.
- Привязка к предмету/конкретному оружию.
- Валидация неизвестных ссылок и циклических зависимостей.
- Предпросмотр **как действие в Adventure** прямо из редактора HB, с фиктивными безопасными ресурсами.

**Не ломать старый HB JSON.** Новые механические поля необязательны. Существующие описания переходят на уровень 3; структурированные старые механики, уже поддерживаемые `spell.mechanics`, мигрируют в уровень 1/2 с тестами. Зафиксированный HB-снимок игрового героя остаётся неизменным при правке общей библиотеки.

## 17. Техническая архитектура: как встроить без второго игрового движка

### 17.1 Сейчас

Ключевые файлы, которые уже проверены в `main`:

- `app/GameMode.tsx` — интерфейс, вкладки, вызовы событий;
- `app/adventure.ts` — `AdventureState`, здоровье, концентрация, инвентарь, кубики, отдых;
- `app/DiceTray.tsx` — отдельная панель кубиков;
- `app/PlayInventory.tsx` — UI предметов;
- `app/playSpells.ts` — вывод механического профиля заклинания;
- `app/combat.ts`, `app/initiative.ts` — атаки и инициатива;
- `app/characterResources.ts`, `app/restRules.ts` — ресурсы и отдых;
- `app/homebrewEngine.ts`, `app/homebrewMagic.ts` — HB;
- `app/characterRules.ts`, `app/multiclass.ts` — параметры героя;
- `app/exportFormats.ts`, `app/characterFiles.ts` — состояние и экспорт;
- `app/game-mode.css` и `app/ThemeSettings.tsx` — визуальная тема/настройки;
- `tests/adventure.test.ts`, `tests/playSpells.test.ts`, `tests/browser-sheet.cjs` — нынешние проверки.

### 17.2 Новые **внутренние** модули (предлагаемые имена, не существующие файлы)

```text
app/play/
  rulesetPolicy.ts       // отличие 2014/2024
  modifiers.ts           // значения, бонусы и причины
  rollComposer.ts        // единый план броска, dice AST, crit
  actionCatalog.ts       // оружие + spells + class features + items + HB
  actionExecutor.ts      // preview -> confirm -> immutable transaction
  spellActivities.ts     // расширение существующего playSpells, не дубль каталога
  effects.ts             // концентрация, состояния, длительности
  resources.ts           // единые расход/восстановление с адаптером characterResources
  equipmentEffects.ts    // привязка экземпляров предметов к правилам
  journal.ts             // история, сериализация, отмена
  selectors.ts           // производные данные и объяснение
  migrations.ts          // нормализация AdventureState версии 1 -> 2

app/components/play/
  QuickActions.tsx
  RollComposerDialog.tsx
  ActiveEffectsStrip.tsx
  StatBreakdown.tsx
  RestPreview.tsx
  PlayActionCard.tsx
```

**Важное архитектурное ограничение:** эти файлы не должны стать **параллельным** набором формул по отношению к `characterRules` и `combat`. Нужны адаптеры к единому источнику данных. Рефакторить постепенно: сначала бонусы/броски, затем действия, затем магию/предметы.

### 17.3 События

```text
UI («Использовать») → buildActionPreview(character, actionId, context)
                     → [возможные броски, стоимость, эффекты, предупреждения]
                     → confirm / cancel
                     → executeAction(preview, randomSource)
                     → { nextCharacter, transaction, diceResults }
                     → save existing native JSON / update journal / repaint UI
```

- Расчёт **чистыми функциями**, UI только вызывает их.
- `buildActionPreview` не изменяет состояние и не тратит ячейки.
- Идентификатор транзакции обеспечивает защиту от двойного нажатия и повторной обработки.
- Рандомайзер может подменяться в тестах; production по-прежнему применяет `crypto.getRandomValues`.
- Некорректная формула превращается в понятное сообщение об ошибке, а не в зависание страницы.
- Временные и целевые механики, требующие решения мастера, сохраняют **ручную корректировку**.

### 17.4 Версионирование игрового JSON

- Сохранить `adventure.version: 1` при чтении старых файлов.
- Новый `version: 2` вводить **только после появления валидатора и мигратора**, без изменения основной схемы персонажа там, где это не требуется.
- Миграция `1 → 2`: нормализовать `PlayItem` в `ItemInstance` **без потери `name`, `quantity`, `notes`, `container`, `charges`, custom бонусов**; `PlayEffect` конвертировать в ручной `ActiveEffect`, если детали источника неизвестны; журнал v1 оставить читаемым.
- Действующая копия приключения должна сохранять источник `sourceId`, `startedAt`, снимок HB и возможность редактировать **только копию**.
- Оригинал в Таверне не получает из приключения потраченные слоты, урон и изменения инвентаря.
- Экспорт «Наш JSON» остаётся полным. Форматы LSS/Helpmate могут не поддерживать транзакции/эффекты — **не терять их в родном JSON**, не обещать перенос чужим форматом.
- Не использовать Base64 для хранения JS, не создавать отдельную БД и не вводить новый серверный сервис.

## 20. Что не делать сейчас — конкретный стоп-лист

- [ ] **Нет** комнат партий и пользователей, совместных бросков, приглашений, чата, синхронизации с мастером.
- [ ] **Нет** трекера инициативы других персонажей/монстров. Личный бонус и личный бросок инициативы остаются.
- [ ] **Нет** VTT, карты, токенов, тумана войны, освещения, звука.
- [ ] **Нет** автоматического редактирования других персонажей после передачи предмета, лечения или магии.
- [ ] **Нет** полного боевого ИИ и принятия решений за мастера.
- [ ] **Нет** переписывания существующего конструктора, экспортов, профилей пользователей и визуальных тем.
- [ ] **Нет** полной автоматизации правил из сырых строк описаний и неподтверждённой поддержки всей редакции 2024.
- [ ] **Нет** обязательного подключения сторонних сервисов/платных баз или новых серверных зависимостей для работы персонального листа.

## 21. Рекомендуемый минимальный релиз после 1.6.1

Если цель — **максимальный рост качества игрового режима за один релиз**, выбрать не больше 5 связанных задач:

1. **Поясняемые бонусы**: показатели и броски считают один движок; виден источник каждого бонуса.
2. **Развёрнутый бросок**: обычный один клик остаётся; расширенный режим позволяет на время изменить только этот бросок.
3. **Избранные действия**: основное оружие, часто применяемая магия, расходники и особенности в одной панели.
4. **Безопасное сотворение**: структурированный preview, правильная стоимость/несколько атак, понятный ручной fallback.
5. **Эффекты и восстановление после обновления страницы**: концентрация/временные бонусы и надёжный журнал операций с отменой.

Это превращает 1.6.1 из «рабочего интерактивного листа с множеством полезных функций» в **связный игровой инструмент**, который реально разгружает игрока. После этого без риска наращивать умный инвентарь, отдых, 2014/2024-политики и формы.

### Определение готовности standalone-режима

Можно объявлять режим полноценным личным помощником, когда игрок способен провести обычную сессию **не покидая HeroList для ручного подсчёта стандартных игровых операций**: атака, урон, расход/возврат ресурсов, магия, здоровье, концентрация, состояние, предметы, отдых, развитие копии. При этом нестандартные решения мастера и сложные магические обстоятельства остаются ручными, но не ломают игру.

**Следующий шаг для разработки:** начать с `ModifierEngine + RollComposer`, добавить миграционные и регрессионные тесты, затем подключать единые действия. Не начинать с нового дизайна разделов, пока данные и операции не определены.

## 22. Приложение: вопросы перед реализацией (ответы по умолчанию)

| Вопрос | Предлагаемый вариант, не требующий отдельного согласования на старте |
|---|---|
| Нужно ли запрещать действие, если уже потрачено? | Показывать предупреждение и потребовать подтверждение; полный «строгий» режим — настройка пользователя |
| Могут ли ручные поправки влиять на все броски? | Только явно выбранные цели; есть срок действия и кнопка отключения |
| Как применить урон другой цели? | Показать бросок и скопировать результат; **не** изменять чужой лист |
| Нужен ли общий счёт раундов? | Личный приблизительный счётчик уже есть; не делать его глобальным таймером боя |
| Что делать с неподдерживаемым заклинанием? | Описание + ручной бросок + ручная трата, с уведомлением об отсутствии автоматизации |
| Что делать с множественными источниками одинакового оружия? | Привязывать атаку к `ItemInstance.id`, не угадывать по названию |
| Должно ли всё сохраняться после обновления? | Да: HP, эффекты, ресурсы, инвентарь, последние события, отменяемые изменения; временное открытие меню — необязательно |
| Следует ли вводить новую базу данных? | Нет, базовым остаётся существующий native JSON и текущая схема сохранений |
| Можно ли сделать оформление «как у конкурента»? | Брать **взаимодействия и UX-принципы**, не копировать визуальный дизайн, исходный код или защищённые тексты |

---

**Итого:** фокус исключительно на standalone. HeroList должен стать самым удобным местом **играть уже созданным героем** — с проверяемыми расчётами, быстрыми действиями и сохранёнными последствиями. Будущие сетевые и мастерские возможности смогут использовать тот же движок, но **в текущий объём работ не входят**.
