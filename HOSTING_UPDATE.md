# Обновление HeroList на хостинге из готового main

Папка [main](https://github.com/ThrandenSeverest/list-geroya-5e/tree/main) содержит
исходники и уже скомпилированный `dist/`. На хостинге нужно подтянуть готовые
файлы, установить production-зависимости при необходимости и перезапустить
frontend. Компиляция на хостинге не требуется.

## Что подготовлено в main

| Файлы | Назначение |
| --- | --- |
| `dist/client/` | Готовые клиентские файлы и изображения |
| `dist/server/` | Готовый серверный frontend для Node.js |
| `dist/BUILD_INFO.json` | Версия, исходный коммит и время локальной сборки |
| `deployment/start-frontend.mjs` | Запуск готового dist без сборки |
| `package.json`, `package-lock.json` | Зафиксированные зависимости |

`vinext` **уже перенесён в `dependencies`** в `package.json`, вместе с
`react` и `react-dom`. Устанавливать его отдельно или глобально не нужно.
Пакеты для компиляции находятся в `devDependencies` и для запуска не нужны.
Собственные транзитивные зависимости Vinext npm устанавливает автоматически.

Нужен Node.js **22.13.0 или новее**. Команды для готовой версии:

```bash
npm ci --omit=dev --ignore-scripts --legacy-peer-deps
npm start
```

`--legacy-peer-deps` используется и в штатном скрипте обновления: установка
не добавляет дополнительные peer-пакеты инструментов сборки. Lifecycle-скрипты
пакетов не выполняются; приложение запускается отдельно через `npm start`.

## Обычное обновление только frontend

В выпуске 1.5.2 backend, схема базы и настройки авторизации не менялись.
Для этого обновления **не нужно заменять backend или запускать миграции**.
Существующий API и подключение к Telegram используют прежние настройки.
Запуск frontend проверен отдельно; вход через Telegram нужно проверить на
вашем домене с вашим работающим API.

Копируйте только следующие пути из main в рабочую папку приложения:

- `dist/` — заменить целиком.
- `deployment/start-frontend.mjs`.
- `package.json` и `package-lock.json`.

Перед заменой остановите **только frontend** вашим существующим менеджером
процессов. Сохраните предыдущие runtime-файлы для отката. После замены
установите production-зависимости в рабочей папке и перезапустите тот же
frontend-сервис. При неизменном lock-файле и уже установленных зависимостях
повторная установка не нужна.

Пример переноса через rsync (frontend должен быть остановлен):

```bash
# Замените эти абсолютные пути своими.
# SOURCE_DIR — чистая копия main; APP_DIR — рабочая папка приложения.
SOURCE_DIR=/srv/herolist-source
APP_DIR=/srv/herolist

# Проверки должны пройти перед переносом.
test "$SOURCE_DIR" != "$APP_DIR" &&
test -f "$SOURCE_DIR/dist/server/index.js" &&
test -f "$SOURCE_DIR/dist/BUILD_INFO.json" &&
test -d "$APP_DIR" &&
mkdir -p "$APP_DIR/dist" "$APP_DIR/deployment" &&
rsync -a --delete "$SOURCE_DIR/dist/" "$APP_DIR/dist/" &&
cp "$SOURCE_DIR/deployment/start-frontend.mjs" "$APP_DIR/deployment/" &&
cp "$SOURCE_DIR/package.json" "$SOURCE_DIR/package-lock.json" "$APP_DIR/" &&
(cd "$APP_DIR" && npm ci --omit=dev --ignore-scripts --legacy-peer-deps)

# При успешном завершении перезапустите существующий frontend-сервис.
```

Эти команды не заменяют backend и не удаляют файлы за пределами `dist/`.
Не используйте `rsync --delete` для всей рабочей папки приложения.

## Как подтягивать main через Git

Используйте отдельную чистую копию репозитория как источник готовых файлов:

```bash
# Один раз; папка назначения должна быть новой.
git clone --branch main --single-branch \
  https://github.com/ThrandenSeverest/list-geroya-5e.git /srv/herolist-source

# Для следующих обновлений.
git -C /srv/herolist-source pull --ff-only origin main
```

Затем перенесите runtime-файлы по инструкции выше. Не запускайте frontend
из `/srv/herolist-source`: запуск обновляет служебные секреты в трёх файлах
`dist/server/`, и Git видит локальные изменения. Отдельная рабочая папка
позволяет делать `git pull` без этих конфликтов.

Если рабочее приложение уже находится внутри Git-копии, используйте отдельную
копию main для следующих обновлений. Не сбрасывайте изменения работающей
копии вслепую. Папка `.git` не нужна для запуска готового приложения.

## Сохранение пользовательских данных

Обновление только frontend описанным выше способом сохраняет:

- `.env`, `backend/.env`, настройки API и конфигурацию systemd/PM2;
- `backend/data/`, SQLite, `uploads/`, `saves/` и остальные пользовательские
  каталоги за пределами runtime-путей;
- прежние `DATABASE_URL`, настройки Telegram, домен и протокол сайта;
- хранилище браузера: оно не очищается обновлением frontend.

Локальные персонажи привязаны к домену и протоколу. При открытии другого
адреса браузер может показать отдельное пустое хранилище.

По умолчанию backend использует `sqlite:///./data/list-geroya.db`, но
реальный путь определяется вашим `DATABASE_URL` и рабочей папкой API.
Перед обновлением сохраните резервную копию **именно этой базы** и ваших
пользовательских файлов. Для SQLite есть `backend/scripts/backup_db.py`,
использующий SQLite Backup API. Перед запуском проверьте, что путь указывает
на существующую базу:

```bash
# Подставьте реальный абсолютный путь из настроек API и путь резервной копии.
DATABASE_FILE=/srv/herolist/backend/data/list-geroya.db
BACKUP_FILE=/var/backups/herolist/list-geroya-before-update.db

test -f "$DATABASE_FILE" &&
test ! -e "$BACKUP_FILE" &&
python3 /srv/herolist-source/backend/scripts/backup_db.py \
  "$DATABASE_FILE" "$BACKUP_FILE"
```

В репозитории нет рабочей базы, аккаунтов, uploads/saves и рабочих `.env`.
`backend/.env.example` — только пример, его не следует копировать поверх
существующей конфигурации. При переезде на другой хост база и пользовательские
файлы переносятся отдельно; загрузка main сама их не переносит.

## Полное обновление backend — отдельная операция

`deployment/update-hosting.sh` обновляет frontend **и backend**. Используйте
его только когда действительно нужен новый backend, после настройки
`/etc/herolist-update.conf` по `deployment/herolist-update.conf.example`.

Скрипт читает путь SQLite, останавливает указанные сервисы, создаёт и проверяет
резервную копию базы, заменяет код, устанавливает зависимости и выполняет
Alembic-миграции. Рабочие `.env` и стандартные каталоги данных не заменяются.
При ошибке он восстанавливает предыдущие `dist` и backend-код; **это не полный
откат зависимостей и миграций базы**. Для frontend-выпуска 1.5.2 используйте
обычное обновление выше.

## Проверка после обновления

1. Убедитесь, что frontend-сервис работает и главная страница открывается.
2. Сверьте версию в истории обновлений и локальном `dist/BUILD_INFO.json`.
3. Войдите через Telegram на прежнем домене и откройте существующего
   персонажа и Homebrew из прежнего аккаунта.
4. Если нужен откат, верните сохранённые runtime-файлы, установите зависимости
   по прежнему lock-файлу и перезапустите frontend.

Не выполняйте `npm run build`, `vite build` или `vinext build` на хостинге.
Для запуска готовой версии не нужны исходники `app/` или devDependencies;
удалять исходники для обновления необязательно.

## Как готовятся новые выпуски

Frontend компилируется **локально на машине разработчика/ассистента**:

```bash
bash scripts/build-committed-dist.sh
```

Скрипт устанавливает зависимости сборки, выполняет тесты и компиляцию,
заменяет служебные build-секреты заглушками и записывает `BUILD_INFO.json`.
Исходники и готовый `dist/` публикуются вместе в `main`. GitHub Actions
независимо пересобирает и сравнивает результат, но не переписывает
production-папку `dist` в main.

GitHub Pages имеет отдельную статическую сборку и режим локального аккаунта.
Для Node.js-хостинга берите **main/dist**, а не ветку `gh-pages`.

Готовая версия 1.5.2 дополнительно проверена локально с установкой
`npm ci --omit=dev --ignore-scripts --legacy-peer-deps`: главная, `/account`
и статические файлы открываются без Vite, TypeScript, Next.js и Vite-плагинов.
Тестовые файлы данных и конфигурации при запуске остались неизменными.
